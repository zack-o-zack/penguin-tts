# Penguin TTS — Product Requirements Document

**Status:** Draft for product review  
**Version:** 0.1  
**Updated:** November 6, 2026  
**Release focus:** macOS on Apple Silicon M1 or newer  
**Product promise:** Switch providers, not your workflow.

This PRD converts the discovery discussion into requirements for the first public release. Confirmed requirements reflect the founder's answers. Proposed release boundaries, targets, and scope reductions are recommendations and have not been separately approved. No implementation or performance result is implied.

## 1. Product summary

Penguin TTS is an open-source desktop app for turning text into speech using a user's own cloud API keys, a self-hosted server, or a supported model running on their computer. Users choose a voice and language, generate a clip, listen, and export through one consistent interface.

The initial product serves short clips and straightforward narration. It makes source choice accessible without requiring users to learn a different creation workflow for every provider. A future Penguin-hosted paid service can become another source without making accounts or subscriptions necessary for local or BYOK use.

## 2. Problem and opportunity

The product hypothesis is that users want more control over speech generation cost, privacy, and provider choice, but do not want the setup work or fragmented workflows that can accompany that control. This hypothesis comes from founder discovery; it has not yet been validated through customer interviews or usage data.

The opportunity is to make three choices available in one approachable product: use a cloud provider with an existing key, use a self-hosted service, or run speech generation locally. Penguin should make each choice understandable and preserve the user's work when they change sources.

## 3. Audience and jobs to be done

The confirmed audience is broad. These initial use cases are hypotheses for usability testing, rather than validated customer segments:

| User situation                           | Job to be done                                                   | Desired outcome                                             |
| ---------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------- |
| Someone needs a short spoken clip        | Paste text, find a suitable voice, and export audio              | A useful clip without learning an audio editor              |
| A creator has a preferred cloud provider | Use an existing API key and compare available voices             | Control over source and spending within a familiar workflow |
| A user prefers local processing          | Install a supported model and generate without sending text away | Speech that works offline after installation                |
| A user operates a compatible TTS server  | Connect its endpoint, model, and voice                           | Use that server through the same editor and player          |

## 4. Goals and boundaries

### Goals

- Make the text-to-clip workflow understandable to a general audience.
- Support local, BYOK, and compatible self-hosted generation through the same workflow.
- Preserve text and compatible preferences when sources change.
- Provide useful voice and language discovery based on actual engine capabilities.
- Keep the interface responsive while speech generation or downloads run.
- Store user work locally and make exports useful outside Penguin.
- Deliver an open-source app with Mac App Store distribution as the target.

### Outside the first public release

Confirmed deferrals: voice cloning, batch generation/export, accounts, sync, cloud backup, and the optional paid Penguin service.

Proposed deferrals: multi-speaker editing and per-speaker exports; a timeline, effects, pitch editing, pronunciation dictionaries, word-level alignment generated by Penguin, and packaged Windows/Linux releases. These scope choices keep the first release aligned with the requested simple editor. Windows/Linux remain product direction, and per-speaker exports remain a requested follow-up.

Supporting small and large local models is product direction. Public v1 must have at least one verified local model; an unrestricted promise to run every model is not part of the proposed release.

## 6. Core user journeys

### A. First local clip

The user opens Penguin without an account, chooses local generation, sees a compatible model's download size and language coverage, and installs it. They choose a voice and language, enter text, generate, listen, and export. Installation failures explain what happened and provide a recovery action. Once the model is installed, the same journey works without a network connection.

Whether one model is bundled for first-launch offline use is an open packaging decision. Do not describe the app as usable offline before the required model is available.

### B. First BYOK clip

The user adds a provider connection in Settings, saves a key, and tests the connection. They return to the editor, select an available voice/language, generate, and export. Before generation, the interface identifies the remote source. Missing or invalid credentials produce an actionable connection error without discarding text.

### C. Switch source while editing

The user changes source after entering text. Their text remains. Compatible language and speed settings remain; incompatible voice/model selections require a new choice. Previously used source-specific choices are remembered. Changing source during generation requires cancellation or an explicit next-generation choice; it must not reroute an in-flight request silently.

### D. Connect a self-hosted server

The user supplies a base URL, authentication if needed, and model/voice identifiers. A connection test explains whether the endpoint satisfies the supported speech contract. If discovery is unavailable, they enter identifiers manually. An unsupported API is identified as incompatible rather than shown as a broken cloud account.

### E. Reuse and export a result

The user reopens a result from local history, sees its original text and settings, and plays or exports saved audio without generating again. They can export a combined clip, individual paragraph files, or subtitles with an explicit timing granularity. Generating from edited text creates a new result and leaves the earlier completed result accessible.

## 7. Functional requirements

Acceptance criteria below apply to public v1 unless an earlier milestone is specified.

### FR-01 — Editing and input validation · P0

The editor accepts plain text and preserves paragraph boundaries. It displays character count and applicable source limits. Empty or unsupported input prevents generation with a clear explanation. Editing, switching sources, and failed requests do not clear the draft. Draft recovery across restart is proposed P1; completed history is P0.

**Acceptance:** A multi-paragraph draft survives source changes and an induced request failure. An over-limit request is rejected or offered an explicit supported segmentation path before submission; text is never silently truncated.

### FR-02 — Connections and credentials · P0

Users can add, test, edit, and remove provider/custom connections. Credentials use platform secure storage and are scoped to their connection. Secret values must not appear in history, exports, diagnostics, or logs; the UI may accept a key for entry but must not retrieve saved secrets for display.

**Acceptance:** A saved connection works after restart, an invalid key produces a useful error, and removing the connection removes its saved credential. Inspecting an exported result or application log reveals no API key.

### FR-03 — Voice and language selection · P0

Voices are searchable and filterable by supported language. The UI exposes only combinations supported by the chosen provider, model, and runtime. Human-readable names are preferred; custom identifiers remain available when discovery is unsupported.

**Acceptance:** Selecting a language limits available voices appropriately. An unsupported combination cannot start a request. Changing sources preserves supported choices and visibly requests replacements for incompatible choices.

### FR-04 — Basic and advanced controls · P0

The basic view contains source, voice, language, text, Generate/Cancel, playback, and Export. Synthesis speed appears only where supported. Advanced settings expose relevant model, format/quality, and provider-specific controls without presenting unlike parameters as equivalent universal settings.

**Acceptance:** Unsupported controls are absent or explained. A synthesis speed value reaches a supporting engine. Player speed is labeled separately and never silently substitutes for synthesis speed.

### FR-05 — Generation lifecycle · P0

A request has an understandable queued/loading/generating/completed/failed/cancelled state. Users can cancel without losing their draft. Results retain source, voice, language, model, settings, and creation time. An engine that provides incremental audio should support early playback where the packaged playback path permits it.

**Acceptance:** Success, failure, and cancellation each leave a consistent state. Cancelling stops local work or requests remote cancellation where supported, stops playback, and releases local resources. Any continuing remote computation or possible billing is explained. No cancelled result is presented as complete, and failed paid requests are not automatically retried without user action.

### FR-06 — Local model management · P0

The Models area shows supported model versions, size, language/voice coverage, installation state, license information, and hardware guidance when verified. Users can download, cancel, recover an interrupted download, and remove a model. Corrupt or incomplete artifacts cannot become selectable for generation.

**Acceptance:** Test success, interruption, insufficient storage, corrupt artifact, and removal. An installed compatible model generates with network access disabled. Removing a model preserves previously generated audio and explains that future generation requires reinstalling it.

### FR-07 — Custom endpoint compatibility · P0

The initial custom server contract is OpenAI-compatible speech generation with configurable base URL, authentication, model, voice, and supported output format. Arbitrary APIs require separate adapters; custom endpoint support must not imply universal compatibility. Loopback HTTP is supported; remote connections normally use HTTPS, with any remote HTTP exception explicit.

**Acceptance:** A compatible self-hosted endpoint generates playable audio. A server without discovery supports manual identifiers. Incompatible responses produce clear errors. Authentication is not forwarded to a different origin through redirects.

### FR-08 — Playback · P0

Users can play, pause, seek available completed audio, and see duration/progress. Generating or loading audio does not block editing or navigation. Each player's text and source metadata correspond to the selected result.

**Acceptance:** A completed saved clip plays without regeneration. Seeking and replay work after generation completes. Selecting another result does not continue displaying the prior result's metadata as if it were current.

### FR-09 — Audio export · P0

Users can export WAV or MP3 regardless of the source's original audio format. For multi-paragraph text, users can export a combined narration or numbered paragraph files. The exported combined audio uses the same segment audio and pause policy as the individual outputs.

**Acceptance:** Both formats open in an external player. Paragraph files retain order, the combined result contains every paragraph once, and export failures allow retry without another synthesis request. Per-speaker export is unavailable until speaker assignments are implemented.

### FR-10 — Timestamps and subtitles · P0

Users can export documented cue timing metadata, SRT, and WebVTT. Cue boundaries derive from actual segment audio or supplied alignment. The UI and exports identify whether timing is paragraph/cue-level or word-level. Public v1 guarantees cue-level timing; word-level timing is optional when supplied accurately by a provider.

**Acceptance:** Cues are ordered, have valid start/end times within the final clip, and account for inserted pauses. Subtitle text matches the generated text. Timing is never fabricated by dividing duration across words. Segment generation needed for these exports is explained before generation because it can affect latency and prosody.

### FR-11 — Local history and deletion · P0

Completed generations retain their text, settings, metadata, and audio locally. Users can reopen, export, and delete saved generations without a Penguin account. The app identifies where saved content resides and how to remove it.

**Acceptance:** A completed result survives restart and replays offline. Deleting it removes its app-managed audio and metadata without deleting files the user previously exported elsewhere. Old audio remains usable if its provider connection or local model is removed.

### FR-12 — Understandable failures and cost · P0 / P1

P0 errors cover invalid credentials, rate limits, provider downtime, incompatible endpoints/settings, missing models, insufficient storage, corrupt downloads, and engine failure. Each error offers a relevant recovery action. Reliable generation price estimates are P1; unavailable estimates are shown as unavailable rather than zero.

**Acceptance:** Each supported failure state is exercised without lost text or corrupted saved results. Any shown estimate identifies its basis and is labeled an estimate; local execution is not described as having no hardware or energy cost.

## 8. Quality, privacy, and performance requirements

| Area           | Requirement                                                                                                                                              | Validation                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Responsiveness | Editor, navigation, progress, and Cancel remain responsive during synthesis/downloads                                                                    | Exercise all controls during a representative local run and interrupted download                                    |
| Performance    | Publish only measured latency and hardware guidance; distinguish cold model loading, warm first audio, total time, and peak memory                       | Record hardware, model/version, input, thread settings, and repeated runs; M1 claims require actual M1 measurements |
| Privacy        | Text, audio, and history remain local except requests the user makes to their chosen remote source; no Penguin account required                          | Inspect network activity for local/offline generation and confirm remote destination for cloud/custom generation    |
| Accessibility  | Core creation and export work by keyboard and VoiceOver; controls have useful names and status changes are conveyed                                      | Complete the primary journey with keyboard and VoiceOver                                                            |
| Reliability    | Failed/interrupted work cannot masquerade as a complete model or generation; completed assets survive restart                                            | Interrupt downloads and generation, restart, and inspect selectable models/history                                  |
| Distribution   | Public macOS release meets signing, sandbox, and selected distribution-channel requirements; dependencies and bundled artifacts have documented licenses | Test a packaged installation, retain dependency notices, and validate the store submission path                     |
| Extensibility  | Adding a source or optional Penguin service preserves the editor workflow and existing saved work                                                        | Integrate a second adapter without introducing a separate creation flow                                             |

Numerical latency, memory, minimum macOS version, and installation-size budgets are intentionally open until the packaging/inference proof produces a baseline. Responsiveness is a release requirement; no unmeasured generation-speed promise is approved.

## 9. Success measures

These are proposed validation targets, not observed results or market benchmarks. Collect initial evidence in consented usability sessions and local engineering runs; this PRD does not authorize production analytics.

| Measure               | Proposed target                                                                                                                | Method                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Core task completion  | At least 8 of 10 representative first-time testers generate and export a clip without facilitator help after a source is ready | Observe local and BYOK journeys separately; record setup failures separately              |
| Source switching      | At least 8 of 10 testers switch between two configured sources and generate again without losing text or needing help          | Seed a draft and compatible/incompatible voice cases                                      |
| Offline functionality | All agreed acceptance fixtures generate/play/export successfully with an installed local model and network disabled            | Repeatable packaged-app acceptance suite                                                  |
| Export correctness    | All agreed fixtures pass format, segment-order, duration-boundary, and subtitle checks                                         | Automated artifact inspection plus listening spot checks                                  |
| Perceived usability   | At least 8 of 10 testers can identify where their text will be processed before generating                                     | Ask users to identify local versus remote sources                                         |
| Speed and quality     | Establish baseline before setting numerical launch targets                                                                     | Measure actual M1 generation and run listening checks for every advertised local language |

Launch feedback should inform whether to prioritize more providers, more model families, or richer editing. Downloads and installs alone do not demonstrate that users can create useful clips.

## 10. Delivery milestones and release gates

### M0 — Packaging and inference proof

Deliver a minimal Apple Silicon app that loads one candidate local model, generates playable speech, and exercises the intended sandbox and audio delivery path. Verify model data downloads separately from executable/runtime packaging. Record cold/warm performance, memory, cancellation, licenses, and unresolved App Store questions.

**Exit:** A working packaged local-generation path and a documented decision on the framework/runtime candidate. Signing/App Store access limitations are recorded explicitly; an unsigned development run does not count as store validation. A schedule is set from this evidence rather than a fixed speculative spike duration.

### M1 — First usable build

Deliver the basic editor, one cloud provider, one compatible custom endpoint, one local model, model management, secure credentials, cancellation, playback, WAV export, and local history.

**Exit:** Real local and authenticated cloud runs, a real compatible custom-server run, offline generation after installation, and restart/error recovery pass the applicable requirements. Mocks alone do not establish integration completion.

### M2 — Public v1

Complete all P0 requirements, including all four named cloud providers, MP3, paragraph/combined exports, cue timings, and subtitles. Complete usability, accessibility, artifact licensing, packaged installation, and distribution validation.

**Exit:** P0 acceptance criteria pass, major usability issues are resolved, each advertised provider/model/language is verified, and the release is accepted for the intended distribution channel. Missing provider credentials or store access remains an explicit release blocker rather than an assumed pass.

| Risk or dependency                                                      | Product impact                                                   | Planned response                                                                                                                      |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| App Store treatment of model downloads/runtime packaging is unresolved  | Could prevent the requested distribution arrangement             | Validate a representative packaged app early; retain the App Store goal and make any distribution change an explicit founder decision |
| Local engine, phonemizer, model, or encoder licensing conflicts         | Could block redistribution or require a different implementation | Inventory exact shipped artifacts and licenses before committing to a runtime or project license                                      |
| Large models exceed baseline hardware limits                            | Slow generation or failed installs                               | Start with one measured model; show verified requirements and gate additional families on validation                                  |
| Provider differences in voices, streaming, limits, and alignment        | Inconsistent controls or misleading feature promises             | Derive availability from adapter capabilities and explain incompatibilities                                                           |
| Segment generation changes prosody or increases requests                | Worse narration or higher cost/latency for export features       | Compare sample outputs; disclose segmentation before generation and reuse saved segment audio                                         |
| Broad audience hides different priorities                               | An interface that suits few users well                           | Test the four initial situations before expanding the editor                                                                          |
| External credentials, signing identity, or review access is unavailable | Real integration/distribution validation cannot finish           | Separate development completion from verified release readiness                                                                       |

Research and source detail: [Distribution and local inference](distribution-and-local-inference.md). Policy interpretations and model/framework candidates must be rechecked when implementing them.

## 13. Technical considerations, not product commitments

Go application services, Wails, a TypeScript interface, and a bundled native inference library/helper are the current engineering proposal. These choices must pass M0; they are not acceptance criteria for the user experience.

Implementation should separate connections, engine capabilities, model installation, generation, audio/export, and local persistence. Preserve paragraph structure and source-specific settings. Runtime installation must not depend on users setting up a development environment. Keep the future paid source independent from local/BYOK access, and retain a path to Windows/Linux without promising untested platform parity.
